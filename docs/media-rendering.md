# 媒体呈现与动图

媒体格式与呈现用途分别处理。GIF、动态 WebP、APNG 等格式即使都由 `<img>` 显示，也不能据此决定导航缩略图是否播放动画。

## 组件职责

| 用途                                                 | 入口                         | 约束                                                           |
| ---------------------------------------------------- | ---------------------------- | -------------------------------------------------------------- |
| 来源、参考图、结果选择、版本快照、素材选择、图集标识 | `AssetThumbnail`             | 请求静态缩略图；加载失败显示图标；不回退原图                   |
| 已有复杂缩略图布局                                   | `mediaThumbnailUrl`          | 与公共组件使用同一静态媒体协议；后续修改布局时可收敛到公共组件 |
| Codex 生成图缩略图                                   | `codexGeneratedThumbnailUrl` | 同一静态语义，额外携带源文件 revision                          |
| 主图、悬停放大、编辑正文、精细比较                   | `AssetMedia` 或原图 `<img>`  | 使用原始媒体；原生支持的动图继续播放                           |
| 图片氛围背景                                         | `ImageAmbientBackdrop`       | 一次采样到静态 canvas；透明或不可采样图片不扩展背景            |

`AssetThumbnail` 只负责媒体，不拥有按钮、选择状态、拖拽或预览弹层。启用 `ambient` 时，父容器提供定位、隔离和裁切。原图和缩略图不得作为同一个节点的隐式加载降级链。

## 静态缩略图协议

1. `asset-thumbnail` 和 `codex-generated-thumbnail` 成功时只返回缓存的静态 PNG。
2. 系统缩略图接口返回空图或拒绝时，进入现有沙箱解码器。沙箱通过 `createImageBitmap` 与画布编码产生静态 PNG，不由页面维护动画格式列表。
3. 两条解码路径均失败时，协议返回不可缓存的 404。不得返回原文件，也不得把占位内容写入成功缓存。
4. URL 的 `representation=still` 将新请求与历史上可能缓存了原动图的 URL 分开。静态 PNG 磁盘缓存继续复用，不清空媒体库缓存，不逐帧生成文件。
5. 相同请求继续共享在途任务；保留并发限制、原子写入和空间关闭时的取消逻辑。取消系统任务后，不再启动备用解码。

调用者通过公共 URL 构造函数请求缩略图，不自行拼接协议地址。原资产标识和路径不变，导出、复制和编辑操作仍定位原文件。

## 扩展格式时

- 在媒体解码层核对 MIME、扩展名、文件头、尺寸校验和沙箱协议支持。显示层支持某格式，不代表备用解码器也已支持。
- 保持“缩略图为静态结果”的契约；不在各页面增加 `mimeType === 'image/gif'` 等分支。
- 主图是否播放与装饰背景是否变化分别决定；CSS 的 reduced-motion 不会替原生图片冻结动画。
- 只有输出表示或解码语义改变时才调整相应缓存标识，避免普通组件改动导致全库重新解码。
- 若需要可控播放、暂停或逐帧检查，应另建播放组件，不把时序状态塞进缩略图组件。

## 排查闪动

先区分原图动画、背景变化、节点重新挂载和媒体请求失败。沿组件、URL 构造、协议、缓存、解码器逐层检查；缩略图成功响应应为 PNG，失败响应不得是原动图。旧 URL 的长期缓存可能让服务端修复暂时不可见。

代码检查能确认呈现契约与失败路径，但不能替代实际闪动复现。进行运行时验收时，应分别观察冷缓存、暖缓存、格式解码失败、切换图片和空间关闭，并记录首屏请求与媒体字节；不要用类型检查或单元测试结果宣称帧率、闪动频率或加载耗时已经改善。
