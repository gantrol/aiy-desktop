# Git 协作约定

公开仓库采用轻量发布分支模型。公开长期分支只有 `main` 和 `develop`；其他公开分支完成后删除。首次公开前的完整内部历史只保存在本地 `private` 分支或独立私有仓库中，绝不推送到计划公开的仓库。

## 分支

| 分支                                             | 用途                                                           |
| ------------------------------------------------ | -------------------------------------------------------------- |
| `main`                                           | 稳定、可发布的公开版本，只通过 Pull Request 更新               |
| `develop`                                        | 下一版本的日常集成分支，普通改动以此为合并目标                 |
| `private`                                        | 首次公开前的本地完整历史；不推送到公开远端，也不与公开分支合并 |
| `feat/<name>`                                    | 新功能，从 `develop` 创建                                      |
| `fix/<name>`                                     | 常规修复，从 `develop` 创建                                    |
| `docs/<name>`、`refactor/<name>`、`chore/<name>` | 文档、重构和工程维护                                           |
| `release/<version>`                              | 临时发布稳定分支，例如 `release/0.3.0`                         |
| `hotfix/<version>-<name>`                        | 已发布版本的紧急修复，从 `main` 创建                           |

分支名使用小写英文和连字符；有任务编号时优先写入，例如 `feat/123-batch-import`。

## 日常开发

1. 从最新 `develop` 创建短期分支。
2. 保持改动聚焦，提交信息采用 `feat:`、`fix:`、`docs:`、`refactor:`、`chore:` 等前缀。
3. 按改动范围运行 `npm run typecheck` 和 `npm test`；需要时补充 lint 检查。
4. 提交 Pull Request 到 `develop`，通过检查和评审后合并。
5. 合并后删除短期分支。

禁止直接推送 `main`。`develop` 也应通过 Pull Request 更新。

## 发布

1. 从 `develop` 创建 `release/<version>`，进入功能冻结。
2. 该分支只接受阻塞修复、文档、版本号和发布配置改动。
3. 验收通过后合并到 `main`，并创建版本标签，例如 `v0.3.0`。
4. 将发布期间的修复同步回 `develop`，随后删除发布分支。

没有并行开发需求时，可以冻结 `develop` 后直接发布，不必创建 `release/*`。

### 首次公开的无历史快照

普通 `release/<version>` 分支保留 `develop` 的历史。如果首个公开版本必须不携带此前任何提交，应把它视为一次单独的公开快照，而不是普通发布分支：

1. 在临时 checkout 或已完成审核的干净副本中整理发布允许清单，不要从带有本地数据、junction、构建产物或未审阅文件的工作树直接创建。
2. 使用 orphan 分支创建新的根提交，只加入源码、运行时资源、教程、发布配置和必要的许可证文件。
3. 不把这个无历史快照与带有旧历史的 `main` 直接合并；公开仓库应以该根提交作为起点，后续再按普通 PR 流程维护。
4. 发布前检查 `git status --short` 为空、`git rev-list --count HEAD` 为 `1`，并确认当前提交同时是根提交。

无历史快照仍然需要通过普通发布门禁；“没有历史”不能替代资源可复现、类型检查、测试、人工冒烟和签名验收。

## 紧急修复

从 `main` 创建 `hotfix/*`，修复后同时合并到 `main` 和 `develop`，并按补丁版本创建标签。

## 公开边界

公开仓库中推送的所有分支及其可达历史都可见。若公开前历史、素材或配置不能公开，应先完成清理，或使用独立的私有仓库；不要依赖分支名称隔离私有内容。公开源码不等于开源授权，代码与第一方资源的使用边界以仓库根目录 `LICENSE` 为准。

旧 `master` 在迁移时改名为本地 `private`。首个通过公开检查的版本以 orphan 根提交进入 `main`，随后从该公开根提交建立新的 `develop`；`private` 与公开分支不共享历史。
