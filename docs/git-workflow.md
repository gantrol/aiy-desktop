# Git 协作与发布约定

本文只描述公开仓库中的协作和发行规则。候选版本在进入公开引用之前必须完成整理与审核；未完成的实现、临时分支和维护过程不属于公开发布物。

## 公开引用

| 引用                                             | 用途                                                       |
| ------------------------------------------------ | ---------------------------------------------------------- |
| `main`                                           | 唯一长期公开分支；每个提交都必须是可审阅、可构建的公开状态 |
| `feat/<name>`、`fix/<name>`                      | 面向公开仓库的短期功能或修复分支                           |
| `docs/<name>`、`refactor/<name>`、`chore/<name>` | 面向公开仓库的文档、重构和维护分支                         |
| `hotfix/<version>-<name>`                        | 从已发布的 `main` 创建的紧急公开修复分支                   |
| `v<version>`                                     | 指向已完成发行验收的版本标签                               |

公开仓库不要求长期维护 `develop`，也不要求为维护者发布过程保留远端 `release/*`。短期公共协作分支完成后应删除。

## 公共贡献

1. 从最新 `main` 创建短期分支。
2. 保持改动聚焦，提交信息采用 `feat:`、`fix:`、`docs:`、`refactor:`、`chore:` 等前缀。
3. 按改动范围运行格式、lint、类型检查、公开 smoke 和构建检查。
4. 通过 Pull Request 合并到 `main`；PR 中只讨论可以公开的代码、证据和发布信息。
5. 合并后删除短期分支。

Pull Request 是公共协作和公共 CI 的入口，不是维护者发布最终快照的强制步骤。没有公共评审或分支保护要求时，维护者可以在本地完成发行门禁后，将单个最终提交 fast-forward 到 `main`。

## 发行快照

公开发行只接收最终状态，不接收候选整理过程。每次发行必须满足：

1. 候选提交直接基于推送前最新的 `origin/main`，不改写已公开历史。
2. 候选相对 `origin/main` 只包含本次准备公开的最终提交；提交信息和发布说明不记录非公开过程。
3. 所有新增或修改文件均通过公开性、许可证、素材权利、凭据和打包输入审核。
4. 应用版本、数据库 revision、扩展 manifest、内容包和更新元数据彼此一致；同次发行最多推进一个目标版本。
5. 在最终提交上完成仓库规定的格式、lint、类型检查、公开 smoke、生产构建和适用的平台验收。
6. 推送时明确指定 `main` 和需要创建的发行标签，不推送无关本地分支或标签。
7. 发行完成后删除不再需要的短期候选分支。

版本标签在最终安装包和兼容性验收完成后创建，例如 `v0.3.2`。构建目录 `release/` 是本地产物目录，与 Git 分支无关，不能作为源码输入提交。

## 紧急修复

从最新 `main` 创建 `hotfix/*`。完成目标检查和发行验收后，将修复提交合入或 fast-forward 到 `main`，再按补丁版本创建标签。修复必须保留在后续发行快照中。

## 公开边界

- 任何推送到公开仓库的分支、标签、提交及其可达对象都应视为公开信息。
- 不使用分支名称、Draft PR、删除远端分支或后续改写来保护不应公开的内容。
- 禁止推送凭据、内部测试资产、用户数据、生产内容、临时构建物或未确认权利的素材。
- 最终 `main` 与上一公开版本之间的净差异始终可被比较；不应公开的文件必须在进入公开提交前排除。
- 禁止对公开远端使用 `git push --all` 或 `git push --mirror`。

安装包输入和资源复现要求见[发布输入与安装包边界](release/packaging-inputs.md)。
