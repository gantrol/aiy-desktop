## 已接入的 CLI 原型

入口为 `node scripts/model-training.mjs`，按需构建独立命令进程。无自动下载、主库迁移或默认模型切换。真实训练数据由开发者选择本地目录，产物不进入 Git 或公开测试资料。

| 命令                          | 当前行为                                                                                                                                |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `doctor`                      | 检查 Python、PyTorch、CUDA 与设备能力                                                                                                   |
| `catalog`                     | 只读选取当前可见图片，保留身份、内容哈希与路径                                                                                          |
| `dictionary`                  | 从已审核词条、已有翻译／别名及配图记录分层抽取训练种子，可排除已有数据的内容哈希；另输出来源与待复核冲突                                |
| `classify`                    | 分别统计查询、图片的已知零／一／多关系，以及关联组件；报告未知覆盖和确证无结果                                                          |
| `freeze`                      | 校验唯一身份、分组、标签与范围，并发布不可覆盖的数据版本                                                                                |
| `capture`                     | 调用生产图片预处理与 `ImageSearchEncoder`，保存归一化 768 维 Q8 图片／查询输出；绑定模型文件内容摘要                                    |
| `suggest`                     | 在冻结向量上进行双向余弦候选挖掘，每查询默认 5 个近邻与 2 个分散样本，每图 5 个不同查询族近邻；只处理未知配对，排除验收查询，不修改标签 |
| `train`                       | 独立 Python 管理进程与计算子进程，执行有预算的查询残差训练；非人工标签需显式 `--allow-provisional`                                      |
| `pause` / `cancel` / `status` | 登记幂等控制请求与读取状态；`train --resume` 从完整检查点续跑                                                                           |
| `evaluate` / `compare`        | 在同一冻结图片范围内复用生产纯语义排序，按查询族汇总；不会批准部署                                                                      |

当前配方为 `q' = normalize(q + A(Bq))`，训练小型查询后处理矩阵，不对 ONNX 反向传播，也未实现 LoRA。图片与原始查询向量均来自固定生产 Q8 输出；多正例联合计算，只有明确负例进入损失，部分相关与未知排除。最佳验证候选与最后一步分别保存，验证未改善时可以保留零步基线。

任务保存不可变规格、状态、事件、完整 PyTorch 检查点和 JSON 算子产物。数据、模型、实际向量快照与执行器内容摘要参与绑定；恢复检查 Python／PyTorch／GPU 环境，固定 seed、优化器和随机状态。计算子进程退出后才发布终态并释放设备锁；管理进程异常退出后的自动对账、前台搜索抢占、持久队列和阶段重试仍待接入，不能把短训练续跑等同于完整应用恢复。

原型每批最多 256 张图片、512 条查询，只支持已知固定图片库协议，输入 JSON 限 32 MiB；图片单文件限 32 MiB、捕获总量限 512 MiB。多批采集需要保留各自范围，不能直接合并局部召回率或声称覆盖全库。大规模训练前还需实现分片／流式输入及跨批来源去重。

`dictionary` 默认只按配图数量分层，不假定分类键或排除特定内容。需要分类分层时显式传入 `--facet-key KEY`；`--exclude-facet-value VALUE` 可重复指定，且必须同时提供分类键。来源清单记录这组选择条件，便于复核和复现。

词典关联使用 `dictionary_link`，逐图辅助判断使用 `assistant_visual`，只有人工复核才使用 `human`。词典种子全部进入训练侧，不能靠随机拆同义词获得验证集；未关联项保持未知，画质否决保留为冲突待审。`suggest` 是候选生成器，其余弦分数不是最终生产排名或相关性真值。新查询需逐图观察后补写，并形成新数据版本。双向关系及采集预算见[共同设计](../../../aiy-docs/design/pages/model-training.md#图片与查询的双向关联)。

文件 I/O 使用异步有界读取与摘要；词典的同步 SQLite 查询只在显式 CLI 进程运行，限制 10000 词条、40000 查询写法及 20000 关联，不进入 Electron main／renderer。PyTorch 检查点的同步写入限独立计算进程。JSON 通过同盘临时文件和不可覆盖发布保存；没有依赖覆盖旧输入完成“更新”。

以下章节维护后续完整工作台方案；其中 LoRA、导出、SQLite 队列、窄 IPC 和生产采用仍是待实施内容。既有自动化回归不直接覆盖新 CLI 的训练、恢复及候选挖掘逻辑，专项验证范围另行记录。

## 当前差距

- `ImageSearchEncoder` 在同一模型配置下处理 query、document 和 image，运行时为 Transformers.js／ONNX Q8，只提供推理。训练需同底模的可训练原始权重和独立 Python 环境，不能在当前 Q8 ONNX 文件上直接启动反向传播。
- `runtime.ts` 只有一个模型指纹；图片与文稿缓存以该指纹绑定。查询侧微调若继续沿用此结构，会误用查询模型编码文稿，或使所有向量失效，需要先拆分编码责任和版本。
- `content` Worker 目前既生成查询向量，也生成正文向量；查询与素材的路由须覆盖此处，不能只调整图片查询 Worker。
- 现有受管进程有窄消息协议、取消与诊断，可借鉴其结构；180 秒查询超时和搜索视图生命周期不适合小时级训练。训练要有自己的任务与恢复协议。
- 当前只有独立 CLI 与训练进程的局部能力，没有应用内训练环境管理、样本仓库、前台协调调度、候选版本采用和回滚接口。

| 生产行为                                                                          | 实验必须保持或单独比较的条件                                                     |
| --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 查询已经使用 `task: search result \| query: `；文稿使用 `title: ... \| text: ...` | 不把现有检索前缀当成缺陷，不重复叠加处理器前缀；泛标题是否影响排名由真实案例判断 |
| 输出要求 `sentence_embedding` 为 1×768，再做 L2 归一化                            | Python 与导出路径逐项核对 pooling、mask、维度和归一化，不能只比形状              |
| 图片先 EXIF 旋转、最长边 1024、移除 alpha、转 sRGB                                | 比较实际像素与处理器输入，透明图和文字细节另留回归样本                           |
| 文稿仅在首屏且 `advanceIndex` 时最多编码一个片段                                  | 回放必须携带覆盖，不能把尚未索引的正例判为模型漏召回                             |
| 文稿与图片各自的混合检索使用 k=60 的 RRF                                          | 融合配置变化单列为 B1，不冒充训练收益，也不直接混合两种语义分数                  |
| 模型指纹由目录、文件大小与修改时间组成                                            | 只作本地缓存失效键；实验与跨机器产物另用权重、配置及处理器文件的内容摘要         |

## 建议模块边界

采用按需加载的开发者工作面，renderer 复用 shadcn/ui 的表格、页签、列表—详情与局部快捷键；新增文案进入现有中英文 i18n，不把模型参数、目录或进程控制暴露为通用 renderer 能力。

宿主负责样本身份与修订快照、内容选取、任务持久记录、预算、模型包校验和版本切换。训练执行器是独立 Python 进程，固定可执行文件与入口，参数采用结构化任务包；使用 spawn 参数数组，不让 renderer 提交 shell 字符串、任意 Python 脚本或直接连接主库。

执行接口建议为能力检查、提交、读取状态、订阅事件、请求暂停、恢复、取消和取得产物。实现分为本机与后续远程适配器；首版只注册本机实现，不创建无用途的远程服务、账号和供应商配置。

训练依赖、底模原始权重按开发者选择单独准备，普通安装与基础搜索不强制携带 PyTorch/CUDA。能力检查必须实际核对模型加载、目标参数梯度、精度与导出路径，不能只依据 GPU 名称显示“可训练”。不自动下载新的教师模型、重排模型或执行在线翻译。

## 训练后端的具体选择

推荐独立、可单独安装的 Python 包，包含训练核心、轻量任务管理进程和每次运行的训练子进程。本机由桌面宿主通过固定入口启动，首版使用标准输入／输出上的 JSON Lines 协议；以后同一包在远程机器运行，由远程适配器承接连接与文件传输。训练算法不感知窗口、IPC、SSH 或 GPU 租赁供应商。

| 部分         | 首版选择                                     | 责任                                                   |
| ------------ | -------------------------------------------- | ------------------------------------------------------ |
| 计算与模型   | PyTorch、Transformers／Sentence Transformers | 模型处理器、梯度、训练循环、评估；保留现有检索输入约定 |
| 少量参数微调 | PEFT LoRA                                    | 固定底模修订、目标模块和可训练参数清单                 |
| 执行位置     | 本机单 GPU                                   | 分配设备、限制并发、暂停与恢复；以后增加远程实现       |
| 控制通道     | 版本化 JSON Lines                            | 请求响应、进度事件、心跳和取消；大数据通过任务包引用   |
| 持久化       | 后端专用 SQLite 加任务目录                   | 队列、状态、事件、指标、检查点和产物索引               |
| 环境         | 独立虚拟环境与经过验证的依赖锁               | 不改写桌面 Node 环境，不在任务开始时临时升级依赖       |

首版使用 SQLite 持久队列和一个 GPU 执行槽即可。暂不引入 Redis、Celery、Ray、Kubernetes 或外部实验追踪服务；先以桌面表格和已有图表能力消费结构化指标。训练核心与协议有边界，但不为每一项职责建立独立服务。

Sentence Transformers 的 Trainer 可以复用训练、回调与检查点机制；query-only 配方仍需要固定向量的 batch 与损失适配。标准文字／图片三元组训练会重新编码输入，不能直接复制示例后宣称已实现素材向量复用。基线回放先建立，查询侧 LoRA 是优先探针；首版实际支持哪些训练配方由梯度、导出、质量与成本结果决定，不预先锁死唯一配方。

依赖按底模架构 `embedding_gemma2` 核对，不能套用第一代 EmbeddingGemma 或生成式 Gemma 2 的训练／导出结论。模型保存配置中的版本号只是来源线索，不是本机验证过的依赖锁；开发版本还需固定提交。原始权重、模型实现、训练库和导出器分别记录修订，经过实际探针后再锁定安装组合。

## 进程关系与状态归属

```text
炼丹炉 renderer
    │ 窄 IPC：任务身份、配方参数、预算
桌面宿主：选定输入、实验记录、状态投影、模型采用
    │ 本机适配器／以后远程适配器
Python 任务管理进程：持久队列、事件、设备占用、恢复
    │ 每次 attempt 独立进程
训练子进程：模型、GPU、训练／验证／导出
```

任务管理进程保持轻量，不初始化 CUDA；每次 attempt 的子进程持有 CUDA 上下文。训练退出、OOM 或原生故障不会使桌面应用一起退出，子进程结束后释放其 CUDA 占用。Windows 子进程采用 spawn，数据加载器初始使用零 worker，实测需要后再增加少量 CPU worker；不跨进程传输 CUDA tensor。数据库提交与文件读写通过有界任务执行，单独持有 SQLite 连接，不在控制消息循环中执行长时间同步 I/O。

桌面宿主保存实验意图、输入快照、候选采用及后端状态投影；后端的任务数据库是执行阶段与已完成步骤的事实来源。宿主不能仅因“提交成功”写成 RUNNING，也不能与后端各自推进一套状态。请求丢失后按 runId 查询和对账。后端启动时结合进程身份、最近心跳、检查点与退出事实恢复，未确认的状态保持待核对，不凭 PID 存在或缺一次心跳就判成功或失败。

同一设备的租约由管理进程独占；训练、GPU 验证、量化或导出中会占 GPU 的阶段均取得该槽位。控制通道由独立循环读取，训练子进程在可恢复边界消费暂停／取消请求，不能因为长时间模型计算而完全失去控制。stdout 仅输出协议消息，训练库普通日志进入 stderr 或受限日志文件；消息长度、事件积压与日志保留有上限。

后端与训练子进程间采用合作停止加超时回收。明确区分“已请求暂停”“检查点完成”“GPU 已释放”；硬终止时只信任上一份完整检查点。本机宿主退出规则沿共同设计，不能直接套用现有搜索进程的退出即杀逻辑丢掉训练状态。

## 最小任务协议

以下是拟定命令含义，实施时用 TypeScript 与 Python 的严格 schema 对齐；界面只传稳定标识与结构化参数。

| 命令           | 返回或行为                                                   |
| -------------- | ------------------------------------------------------------ |
| capabilities   | 协议版本、支持配方、设备、精度与导出能力；探测结果带环境指纹 |
| submit         | 校验任务包、登记队列，返回 runId／attemptId；不等待训练结束  |
| get / events   | 当前事实状态与带序号的增量事件，支持游标重连                 |
| pause / cancel | 幂等地登记请求，实际生效后另发事件                           |
| resume         | 指定已完成检查点，兼容性检查后创建新的 attempt               |
| artifacts      | 可取回产物的类型、大小、内容摘要和完整性状态                 |

任务包固定 dataset、corpusVectors、recipe、baseModel 与 environment 的版本及摘要，包含随机种子、最大训练时长、步数、磁盘和检查点预算。设备只表达能力与数量需求，实际 cuda 编号由执行器分配。传输目录在宿主和执行器处解析，界面不能提供任意读取路径。

submit 以 runId、attemptId 和规范化任务摘要实现幂等：同一身份、相同内容返回既有任务；同一身份、不同内容返回冲突。重试提交不重置预算，也不另启一个 GPU 子进程。任务状态转换与对应事件在一次事务中提交；事件携带顺序号，主进程只增量订阅，避免全量日志轮询。

每个 attempt 都记录退出码、失败阶段和可恢复检查点。评估或导出失败可以从已有训练产物重试该阶段，不重新训练；最终包完成与否分别记录，不能仅凭训练进程退出码为零就显示“可采用”。

## 后端目录与可迁移产物

建议后端根目录结构如下，具体路径由开发者选择，不进入训练配方：

```text
jobs.sqlite3             任务、事件、摘要指标
objects/<digest>        已选素材、数据集清单与固定向量
environments/<id>       依赖锁及能力探测结果
runs/<runId>/
  spec.json             不可变任务规格
  attempts/<attemptId>/ 阶段日志与运行记录
  checkpoints/          完整恢复状态及清单
  artifacts/            adapter、评估、ONNX／Q8 候选包
```

对象写入与检查点先进入临时位置，完成文件校验后在同一文件系统提交完成标记与清单，再更新数据库引用。恢复、导出与同步只使用已提交的清单；目录存在不表示写入完成。按字节预算回收无引用缓存，活动任务、最佳候选与必要恢复点不能被缓存清理删除。

本机可读数据集对象采用只读引用；迁往远程时只传缺失的摘要对象。模型权重、数据集、运行日志和部署包各自管理，不重复打包全部开发资料库。训练检查点包含优化器等恢复状态，部署包只带推理所需模型、兼容清单与报告，二者不可混称。

## 本机到远程的后端演进

先在 Windows 独立 Python 环境完成真实加载、训练和导出探测，锁定能够工作的一组依赖；若具体依赖无法支持，再明确评估 WSL 执行器，不把 WSL 或 Docker 自动变成桌面的前置依赖。未来 Linux GPU 镜像复用同一 Python 包和任务格式，平台依赖允许各自锁定，环境相似不等于位级可复现。

远程阶段建议先支持连接已租好的单 GPU 机器。上传任务包后，由远程持久管理进程保存队列和控制训练；SSH 连接用于鉴权、控制和增量传输，训练子进程不依附一次易断开的 SSH 会话。未来是否增加 HTTPS API 可独立决定，训练核心不因此重写。

精确续跑仅在训练配置、数据与运行环境满足恢复条件时提供。Windows 到 Linux 或更换 GPU 后须核对数值差异与恢复能力；不满足时提供明确的新实验 warm start。实例租用、续费与回收在后续供应商适配器处理，不能混入 optimizer 或 Trainer 回调。

## 样本与实验存储

开发者选择训练工作目录，保存标注、不可变数据集清单、任务事件和候选；与可重建的 `.cache/image-search` 区分。模型评估数据是功能数据，不能伪装为测试代码；研发专项测试与运行证据继续遵守私有测试仓边界。

样本最小内容：query、意图、类型、模式、候选稳定身份、内容修订／摘要、实际片段或图片引用、人工等级／偏好、错误原因、基线版本、原始排名与分数、索引覆盖。字段使用稳定标识，展示名称由 i18n 解析。记录多个正确结果和未判断状态。

数据集清单固定来源、划分协议及标注版本。选定正文与媒体按内容摘要落成不可变快照，任务中只保存相对对象引用；同步使用异步、有界并发和在途字节预算。未导出的来源发生变化时提示更新到新数据集，不让历史标注悄悄对应新内容。

采集适配器从宿主授权的只读快照取得完整评估目录、内容修订和索引覆盖，再记录实际排名与片段证据。每个捕获结果绑定数据集、范围摘要、查询与意图摘要、模式、编码契约、排序版本、provider 和来源记录。自行填写 `producer` 或重算 JSON 摘要只证明声明一致，不能证明结果经过生产编码器。记录深度与实际返回数量一并保存，不推断未捕获的更深排名。

已知库协议按查询组隔离；新内容协议还需按整个资料目录的来源／近重复组隔离，训练执行器记录实际接触的素材和负例挖掘范围。只检查已判断条目的来源不足以排除未判断素材泄漏。验收组不能进入训练建议队列；缺失查询、冲突判断、修订变化和范围不匹配均应拒绝比较。

实验清单固定基线、数据集及候选库摘要、训练配方、输入前缀、图像预处理、随机种子、环境锁、最大 GPU 时间、最大步数和检查点预算。日志及状态追加保存，有序号和心跳；异常重启后重放状态，不把“训练中”永久留在界面。

## 离线辅助工具的接入边界

样本冻结、环境诊断、评估比较和待标注建议已通过上述 CLI 接入；捕获调用生产编码器，评估复用纯语义排序，但尚未覆盖完整应用搜索服务、混合列表或候选采用。以下约束继续适用于扩展接入。

- 冻结数据保存完整目录、查询组、人工判断来源和数据划分，拒绝冲突及泄漏；样本 schema 不由外部草稿自动成为正式契约。
- 评估保留生产顺序、未知及部分相关，按共同设计的完整覆盖配对与查询族口径汇总；未测成本为 `null`，比较不自动批准候选。
- 标注建议只生成候选及原因，不能改原标签；“建议无结果”若需要单独信号，先定义实际采集来源，不从空排名或所有项均为边缘标注推造。
- 命令只读写显式输入与新输出，环境诊断默认不加载模型；大文件摘要需明确启用并采用有界异步流式读取。输出不得覆盖冻结数据。
- 单一资料范围、仅文稿／图片的离线格式不能代替最终混合列表、成对偏好、分片数据或生产捕获适配器。若用硬链接提交输出，须核对 Windows 目标文件系统与崩溃恢复，不能把 Linux 语法检查当成跨平台验收。

## 查询侧微调的第一条路线

推荐先试同底模的 query-only LoRA：只更新文字查询路由中的低秩参数，文稿和图片路由完全使用冻结的原模型。初始化和冻结要逐参数核对，不能假定任意模块名称与 PEFT 自动匹配都适用该模型。

探针先列出模块全名、参数形状、可训练数量和冻结清单，再选择注意力投影等明确目标；不直接对全部线性层套 LoRA。走可求导的 forward，观察有限梯度和至少两个优化步骤前后的参数变化，不能用推理 `encode()` 或 loss 有数值代替更新证据。LoRA 零初始化分支首步可能尚无梯度，应结合后续更新判断，不要求每个参数每一步均有非零梯度。

训练目标是查询向量与固定素材向量之间的对比关系。固定向量应来自选定生产 Q8 编码器，绑定相同图片预处理、正文分段、前缀、归一化和素材版本；不拿另一套 BF16 文稿向量冒充当前索引。训练查询使用检索前缀，初始浮点查询与生产 Q8 查询的偏差先单独测量。

多个正例使用合适的正例集合或屏蔽策略；人工确认的负例优先。只有部分标注的候选库不能整体当作负例库。配方应说明如何处理同源片段、同图副本、同一查询的多个正例和批内负例。应无结果的查询首先用于校准和评估，不直接塞进需要正例的对比损失。

训练查询路径时可以不加载视觉编码器；固定素材矩阵按规模内存映射或分块读取。只缓存冻结的完整输出；LoRA、共享文字骨干或预处理变化都会使其下游输出变化，不能把旧向量跨训练步骤复用。“冻结视觉塔”也不保证通过共享文字骨干后的图片向量不变。

如果查询侧路线不能解决素材表达不足，再考虑同时训练素材侧。该实验使用新素材指纹和独立候选索引，评估与采用成本必须包含素材重编码，不能与查询侧实验只比训练步骤耗时。

另保留固定生产向量后的查询残差校准作为受限备选，例如 `q' = normalize(q + A(Bq))`。它需要版本化运行时算子、校准与恢复机制，也无法找回原向量丢失的信息；不因参数少就认定质量更好。部分层训练及完整微调暂不分配正式预算，待前述路线的限制和资源测量足以支持时再比较。

## 单机显存与时间预算

先以小批次、代表性长度运行短探测，记录峰值 allocated/reserved 显存、吞吐、验证耗时及运行前可用显存，再在预算内决定 micro-batch。显存余量要考虑显示桌面与现有搜索模型，占用不能用显卡总容量替代。OOM 后只在完整检查点恢复，缩小批次并记录新配置，不在未知梯度状态下偷偷重试。

EmbeddingGemma 2 的官方训练路径要求 BF16 或 FP32，不能默认用 FP16。优先核对 BF16 内核可用性，不支持时给出 FP32 的实际资源估算或不可执行状态。

| 技术                   | 何时使用                   | 需要测量或防止的误解                                   |
| ---------------------- | -------------------------- | ------------------------------------------------------ |
| LoRA                   | 首批查询侧训练候选         | 减少优化器状态；仍有前向／反向激活，不保证线性加速     |
| 长度分组、动态 padding | 查询或正文长度差异明显     | 避免将同意图／同正例集中后制造批内假负例               |
| 梯度累积               | 优化批量超过单次显存       | 不等于扩大对比学习中的跨批负例集合                     |
| GradCache              | 确需更大对比批次且显存受限 | 额外前向和梯度缓存可能更慢；不等于跨步骤复用旧模型向量 |
| 梯度检查点             | 激活内存成为主要瓶颈       | 重计算增加时间，和常规训练做同数据对比后再启用         |
| BF16                   | 设备和训练内核实际支持     | 导出后的 Q8 仍需独立评估                               |

数据加载器按实测瓶颈选择少量有界 worker，图片只解码必要版本，避免预加载完整库。每张 GPU 同时运行一个训练任务；前台搜索需要资源时请求在 optimizer step 后保存并释放训练进程，再按任务预算恢复，避免频繁在每次按键时重启。

训练、验证、采样、缓存和导出分别计时。初版只执行少量明确配方，先共同短预算筛选，再给领先候选更多预算；数据太少时报告不能稳定比较，不用一个百分点的波动自动选胜者。正式候选至少核对不同随机种子的稳定性，保留集不参与选超参数。

技术探针可先设最多 100 个优化步骤或 600 秒计算、任一先到即停；这是建议上限，不是耗时预测，准备和导出另计。按实际加载的模态、可训练参数、优化器状态、激活及桌面占用测量显存，不根据模型总参数或显卡标称容量承诺可训练。训练恢复检查点、梯度检查点、GradCache 与梯度累积各自记录成本，不能互相替代。

## 先验证原模型导出

在给微调增加预算前，固定原社区 ONNX 的实际转换代码与修订，用未训练原权重重走导出。核对生产所需 `model_quantized.onnx`、`vision_encoder_quantized.onnx` 及 external data，保留输入、输出名与处理器配置；token hidden states 不能冒充最终 `sentence_embedding`。未找到转换器或架构注册时登记具体缺口，不据此认定必然可导出或必然不支持。

导出探针比较原浮点、导出浮点与 Q8 的向量、有限值、排序及当前搜索通道，覆盖 CPU 和拟支持的实际 WebGPU provider。采用动态量化、静态量化或 QDQ 图表示时分别记录策略、校准数据和算子支持，不能把这些术语互换。量化可能改变精度，验证方法参考 [ONNX Runtime 量化文档](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)；该文档不证明本模型与 WebGPU 已兼容。

## 独立版本、部署与恢复

建议模型包清单区分 `queryEncoder`、`corpusEncoder`、`preprocessing`、`ranking`、`calibration`、`vectorLayout` 与 `indexManifest`，各自带内容摘要和兼容范围；向量布局明确维度、数值格式及归一化。沿用旧配置时两个编码器指向同一个底模。查询缓存依 query 指纹失效，素材向量缓存依 corpus 和预处理指纹失效；结果快照包含两个指纹及排序版本。query-only 也须证明素材契约未变，不能仅凭同为 768 维就复用索引。

LoRA 训练产物先保存底模修订与 adapter，导出时合并到独立查询权重，再走当前生产兼容的 ONNX Q8 路径。导出能力须先试跑验证，不能假定目前的模型选择器会接受任意 adapter。候选包包含归一化后的 768 维输出约定、输入前缀、运行时兼容和评估摘要。

验证次序：训练前生产基线 → 初始浮点查询基线 → 浮点候选 → ONNX 候选 → Q8 候选 → 实际搜索通道与融合列表。逐阶段判断退化来自训练、导出、量化或排序；校准在最后部署格式上进行。只选择最后少量候选做昂贵全库索引和完整回放。

采用候选先校验包、兼容和所需索引，再原子切换模型包指针；在途查询使用旧版本直至完成或取消，新查询使用新快照，禁止一页混入两版。恢复操作切回完整配对版本；保留期内不先删除旧权重与索引。训练成功不自动替换默认模型。

## 持久任务与以后租用 GPU

生命周期建议：QUEUED、STARTING、RUNNING、PAUSE_REQUESTED、CHECKPOINTING、PAUSED、CANCEL_REQUESTED、CANCELLED、INTERRUPTED、FAILED、SUCCEEDED。准备、训练、验证、导出作为独立阶段字段；连接状态另记，远程断线时不虚构任务已经停止。暂停只在完整检查点已提交且子进程释放 GPU 后显示 PAUSED，硬终止只能恢复最近完整检查点。SUCCEEDED 表示任务规定阶段完成，候选可采用还须通过包、索引兼容与加载／恢复检查。

完整检查点包含 adapter／权重、优化器、调度器、随机状态、采样游标、训练步数、配方与数据集摘要。精确恢复需要兼容的环境、训练拓扑与数据；只带权重重新开始时登记为 warm start，新实验重新计算预算，不伪装成续跑。

本机调用固定入口；远程以后接同一执行协议。任务提交有稳定幂等键，事件以游标重连，素材与检查点按摘要增量传输；连接丢失后先查询原任务，不能重新申请一台机器再提交同一实验。

远程供应商适配器后续单独管理实例租用、时限、费用预算与释放状态。训练结束、取消命令送达和实例停止计费是不同状态；必须取得执行端与供应商的结果，才能报告已停止或已释放。首版仅冻结任务包和恢复协议，不安装远程依赖或绑定供应商。

## 实施顺序与验收

1. 先建立真实案例与生产捕获适配器：固定范围、索引覆盖、人工意图及判断，保留 B0，再按已复现问题逐项形成 B1；离线报告不能代替真实回放。
2. 完成最小技术试跑：原模型导出闭环先行，再验证同底模 query-only adapter 的梯度、固定 Q8 素材向量、查询／素材独立路由和旧配置兼容。根据结果选择配方，这是技术风险验证，不是完整功能。
3. 本机闭环：接入开发者样本工作面、独立训练执行器、预算、单任务调度、检查点、对比、生产格式导出、试用和恢复。界面消费真实执行状态；必须能走完一轮真实训练与部署才称首版完成。
4. 在同数据集上测量后优化缓存、批处理和实验淘汰；记录标注时间、各阶段耗时、峰值内存／显存和检索变化，不能仅凭代码结构宣布提速。
5. 需求稳定后接远程 GPU，复用任务包与训练配方；另验证上传恢复、幂等提交、断线状态及实例释放。

应用与插件版本沿同一次候选规则维护；样本仓库确需迁移时先确认部署情况，不重写已执行迁移。研发现有测试、类型与构建按项目规则执行，未经明确要求不新增测试代码；未覆盖的训练和恢复路径必须如实登记，不用通用回归通过代替专项验证。

技术依据见[共同设计的参考](../../../aiy-docs/design/pages/model-training.md#参考依据与边界)。后端额外参考 [Sentence Transformers Trainer](https://www.sbert.net/docs/package_reference/base/trainer.html) 的检查点恢复入口、[PyTorch Windows FAQ](https://docs.pytorch.org/docs/stable/notes/windows.html) 的 spawn 与 CUDA 进程边界，以及 [EmbeddingGemma 2 模型卡](https://ai.google.dev/gemma/docs/embeddinggemma/model_card_2)的精度和输入约定。查询残差原型的执行结果不能证明上述 LoRA／导出路线已兼容，也不构成质量提升结论。
