# 本地语义图片搜索

搜索工作面提供“关键词”“语义”和“混合”模式，默认关键词。“全部”同时检索当前空间的活动文稿与图片；类型筛选在各模式中保留。关键词模式搜索文稿文字，以及图片的关联标题、显示名、原文件名、资产 ID 和已识别的图片文字，不启动嵌入模型，也不要求启用语义插件。

关键词检索完整结束、没有命中且不存在不可读或覆盖不足时，空状态提供“试试语义搜索”；点击保留查询和类型，由用户明确切换，不自动执行模型。有命中时也可通过搜索栏的模式控件切换。语义模式分别返回文稿片段和画面相似结果，保留各自排序并交替展示，不把两个通道的原始分数直接比较。混合模式在文稿、图片各自的完整候选集合内合并文字与向量排名，再分页；使用 RRF（常数 60），精确 ID／完整图片名称优先。融合分数不作为余弦分数展示，文字命中保留真实依据及高亮。语义插件停用或模型不可用时保留关键词结果，并报告语义状态。

## 功能插件与模型

`com.aiy.image-search` 保留插件身份及同一候选的初始版本 `0.1.0`，展示名称扩展为“语义搜索”，通过白名单 HOST 适配器执行。manifest 与 HOST 契约同时声明图片和文稿的搜索能力，以及读取当前空间活动图片、已保存活动文稿的权限。模型编码、索引与 IPC 分开维护，后续可以外置运行时；本轮没有引入任意插件脚本执行。关闭插件会停止语义索引和查询，关键词搜索继续可用。

运行时采用 Transformers.js 4.3.1、ONNX Runtime 1.30.0 和 Sharp，不需要 Python。处理设备可选自动、CPU 或 GPU，默认自动尝试 WebGPU；自动模式在加载或推理失败时释放会话并回退 CPU，明确选择 GPU 时返回可恢复错误。设置中分别显示查询与索引实际成功执行的后端，尚未执行或已释放的 Worker 显示未运行。枚举到后端不作为模型成功执行的依据。

查询、图片编码和文稿编码分别在宿主管理的独立进程中执行，进程内部保留 Node Worker 接收原子取消标记。ONNX、GPU、Sharp 或缓存 SQLite 的原生崩溃只终止对应执行进程，不能与 AIY 主进程共用崩溃边界。每个 CPU Q8 会话最多使用两个原生计算线程，空闲会话关闭线程自旋，图片解码并发为一。查询 Worker 不加载视觉编码器；索引 Worker 需要文字骨干与视觉编码器，隔离会增加索引期间的内存或显存占用。当前固定 Q8 导出在 Windows DirectML 图片推理时出现动态 Reshape 错误，因此使用 WebGPU，不将 DirectML 放入自动尝试链。其他设备及成品包仍需分别验证。

执行进程异常退出时，在途请求返回失败并停止自动重试；自动设备模式在推理期间发生进程故障后，当前运行时的后续主动重试使用 CPU，并重新同步可见目录。明确选择 GPU 时返回 GPU 不可用。切换配置或重建运行时后重新按设备选择启动，不静默改写用户设置。单次请求最长 180 秒；取消先在图片／扫描边界生效，5 秒内未结束则终止进程。正常退出、停用和空闲回收不触发 GPU 故障回退。

在功能插件设置或图片搜索的配置入口中，选择已准备好的本地模型目录，或下载推荐模型。推荐模型是 [EmbeddingGemma 2 ONNX](https://huggingface.co/onnx-community/embeddinggemma-2-ONNX/tree/daa72c51243991dfcaf9f9137d2c573d8f7790c0) 固定修订的 Q8 文本及视觉编码文件，共约 542 MB；不包含音频权重。自行准备时需要同样的 ONNX 文件结构，不能直接选择 PyTorch 权重。模型许可沿用上游条款。

Windows x64 安装包不再内置 ONNX 原生运行库。首次配置语义功能时，从 UNPKG 下载固定版本 `onnxruntime-node@1.30.0` 的五个原生文件，共约 67 MB，保存到应用数据目录的 `runtimes/onnxruntime-node/1.30.0/win32-x64`；保留完整 CPU／GPU 依赖，不复用 Electron 自带的不同版本 DLL。已有本地模型时仅下载运行库；全新配置合计约 609 MB。macOS 与开发环境仍使用已安装依赖中的原生库。Sharp 图片解码仍随安装包提供，关键词与普通图片处理不依赖这次下载。

模型与运行库下载分别需要插件的可选 Hugging Face、UNPKG 网络权限，且仅由用户点击触发；串行流式写入临时文件，限制大小并逐文件核对固定 SHA-256，完整后才启用。取消或权限撤销会中断传输并清理临时文件，失败可重试，已验证文件可以复用。运行库加载前由宿主与执行 Worker 校验，renderer 不提供下载 URL 或原生库路径。选择目录使用系统文件选择器，不上传文件。下载完成后可离线运行；编码阶段关闭远程模型加载，仅使用本地文件。

模型与运行库均可用时显示“模型已就绪”和“更换模型目录”，不再显示下载入口或要求下载权限。仅模型已配置时显示运行库下载入口，不覆盖已有模型目录。目录选择取消时保留现有配置，且不触发配置完成后的刷新；无效目录在覆盖配置前验证失败，原记录继续保留。

配置保存在应用数据目录的 `image-search-runtime.json`，包含模型目录 `model` 和处理设备 `device`（`AUTO`／`CPU`／`GPU`）；旧配置缺少设备字段时采用自动模式。设备与模型写入按配置文件串行合并，选择或下载模型保留设备选择。下载文件位于该目录下的 `models/embeddinggemma-2-onnx/<revision>`。开发环境可用绝对路径 `AIY_IMAGE_SEARCH_MODEL` 覆盖模型目录，不覆盖设备选择。只加载文字和视觉编码器，查询使用 `task: search result | query: ` 前缀，图片不附加文字前缀，保存归一化的 768 维向量。

## 本机 preview

插件通常默认关闭。preview 脚本可以读取 Git 忽略的 `.tmp/image-search-preview.json`：

```json
{
  "enabled": true,
  "model": "C:/Models/embeddinggemma-2-onnx"
}
```

此文件仅作用于当前 checkout 的 preview，设置插件初次安装时的默认启用状态及模型路径。模型路径通过 `AIY_IMAGE_SEARCH_MODEL` 注入，不自动写入应用的 `image-search-runtime.json`；它与用户通过目录选择保存的配置分别维护，preview 中的环境路径优先。换用其他 checkout、开发启动或正式安装时，若没有保存模型配置，需要重新选择同一目录，无需重复下载。后续用户主动关闭插件仍被保留；不自动联网，不改其他 checkout 或正式安装的配置。也可通过 `AIY_IMAGE_SEARCH_ENABLED=1` 设置初始默认值。

## 范围与交互

- 仅查当前空间内仍有活动素材、创作输出或词典关系的图片；归档或删除导致关系失效时，旧缓存不能让图片重新出现。
- 图片结果显示缩略图，选中后加载原图。双击、Enter 和搜索行打开入口优先进入唯一来源创作并定位图片及版本；多来源按需选择，无来源创作时进入素材详情。旁边的素材图标直接查看该图，名称通过悬停和键盘焦点提示。复用现有菜单完成复制、保存、采用和文件定位；只有明确选择“用默认应用打开”才交给系统应用。
- 来源导航按当前空间重新解析图片、创作和词条的稳定身份，失效或归档目标不跳转。素材详情可通过图片身份直接读取，不依赖当前列表页。共享导航接入搜索、素材卡片、详情、创作／词条图片菜单和素材选择器，使用现有新标签入口及离开保护；选择器的单击仍用于勾选。来源与图集归属分别展示，本次没有新增完整的跨作品使用反查。
- 搜索标签隐藏时保留工作面并暂停请求；返回时，快照未变则保留已经加载的图片页和原焦点，查询、主动刷新或快照变化按原规则重置。新增导航只按需查询单张图片的元信息，不读取原文件、不修改内容或数据库版本。
- 语义结果用一根五段相关度条表示强弱，不显示等级文字、指数、原始小数或百分比；精确命中保留独立标签。无障碍名称和等级说明沿用 i18n，不附带模型分数。按作者选择保留弱相关候选，不自动隐藏。当前 Q8 模型的第一级界线沿用文稿 0.650、图片 0.680；文稿还检查本次查询是否高于空查询背景，见下文。等级是试用提示，不解释为概率，不按当次首尾结果重新缩放，也不增加或删除候选。真实截图、照片、长文与不同权重仍需单独校准。
- 关键词模式的完整名称／ID 优先于部分标题匹配；图片可按关联标题或原文件名的部分文字命中。语义模式按向量排序，不额外插入名称匹配。模型未配置、插件关闭或推理失败时明确显示状态，关键词搜索继续可用。
- 标题优先取可读的素材显示名／原文件名，再取活动创作输出或词典的来源标题；来源标题带创作／词典标记和图片日期，缺少可读标题时使用本地化的未命名图片与日期。机器生成的 ID／哈希名称不占主标题，完整资产 ID 留在提示中。名称与原文件名、来源标题保留为精确检索别名；标题不随查询重写。OCR 提供独立文字片段，不把识别文字改写成标题，也不生成图片描述。
- 切换查询、类型和模式保留当前文稿预览；真正选择另一文稿或图片前先排空原有保存队列，保存失败保留文稿。
- 搜索先返回已完成索引的结果，再连续补齐图片。每次仅编码一张，两张之间至少让出 50 毫秒；查询执行期间不启动下一张，已有图片编码可在独立 Worker 内完成。查询 Worker 读取 SQLite WAL 快照，不等待图片编码；原生计算资源仍可能竞争，不能承诺所有机器都零影响。已完成向量在内容哈希仍匹配时提交，过期结果不能覆盖新内容。
- 工作面可见且有有效查询时约每 1.5 秒更新覆盖状态；隐藏、暂停、输入法组合和切换查询会取消过期任务。失败停止自动重试并保留已有结果，主动刷新重试不可读项目。
- 图片关键词结果按 30 项滚动追加，不等待 OCR 完成。首次查询先排列全部名称／ID 命中和已有 OCR 命中；同一搜索会话中新识别到的命中追加到末尾，保留已显示的顺序和分页位置。后台轮询只更新最后已加载的一页及覆盖状态，不与翻页请求相互取消；翻页也不取消 OCR。查询、主动刷新、来源修订或查询进程重建时重新排序并开始分页。语义／混合模式仍在索引稳定后分页。
- 已返回的结果可以立即选择和打开；已搜索范围暂时没有命中时显示局部无匹配状态，不持续显示首屏加载骨架。关键词模式在底部明确显示图片文字识别状态和该通道的已识别数量；文稿也在索引时并列说明两项。单一图片通道的缺口直接显示通道与原因，不重复总数行；混合模式仍保留按图片身份去重的总数。覆盖不足仍不能解释为整库无匹配。
- 否定条件仍是相似度模型的输入，不是严格的筛选条件。模型分数不解释为命中概率，也不能保证“不要黄色”等要求。

## 实现边界

`image-search:*` 使用现有可信 IPC 注册器。renderer 只提交查询、请求 ID、索引控制和分页依据；文件路径通过主进程素材仓库的异步批量解析取得。模型执行与向量扫描放在独立进程的 Node Worker，不占用 Electron main 或 renderer 执行线程。关键词检索不导入 ONNX 和 GPU 原生库。进程隔离用于限制故障影响，不构成第三方代码权限沙箱。

每次只编码一张图片。PNG、JPEG、WebP、GIF 首帧和可自包含渲染的静态 SVG 先经过独立的输入准备进程，按方向校正、保留宽高比生成最长边 1024 的无损 PNG，再交给模型。模型入口保留 32 MiB／1600 万像素校验，但不再用它提前拒绝原件；原件不变。每个空间最多一个在途查询、一个最新等待查询和一张正在编码的图片；模型 Worker 请求 180 秒超时，无请求 5 分钟后释放，关闭空间时终止。缩图资源边界见下文。

SQLite 缓存的同步调用限定在 Worker 内，每批至多扫描 128 条向量；主进程沿用已有元数据数据库，单次目录查询限 128 条。活动元数据只由查询 Worker 更新，索引 Worker 维护自己的临时可见集合，避免旧目录覆盖新元数据。配置读取、文件校验、模型下载与图片解码使用异步接口。

向量缓存位于空间下 `.cache/image-search/vectors.sqlite3`，可重建，不改变产品数据库迁移版本。记录资产身份、内容哈希、名称与检索别名、标题来源、日期、编码状态与 768 维 Float32 向量；已有缓存增补派生元数据列，保留已完成向量。模型目录、必需文件大小和修改时间、编码版本共同组成指纹。设备选择单独控制会话重启，不改变相同 Q8 权重的向量指纹；更换权重或预处理仍须核对编码兼容性。重启复用向量，图片内容变化才重新编码，改名只更新元数据，更换模型指纹后重建。

每次空间数据变化后的查询重新核对活动目录，移除不再活动的资产；隐藏搜索页时不扫描图库，恢复后补上变化。返回结果、选中预览及打开前再次核对当前可见范围。缓存只承担派生索引，不作为素材备份。

图片元数据、OCR 文字与视觉向量共用 `.cache/image-search/vectors.sqlite3` 中的独立表，按最多 128 项的元数据批次同步。关键词 Worker 不导入嵌入模型，也不更改模型指纹或使已有视觉向量失效。旧的 `metadata.sqlite3` 不再作为查询来源，派生名称从当前活动素材重新同步；没有产品数据库迁移。OCR 绑定资产 ID 与内容哈希，内容变化后重做，改名不重做，失去活动来源后清理。OCR 提交引起快照变化，分页不能拼接不同索引状态。

关键词或混合查询可见且允许继续索引时，独立 OCR Worker 每次最多读取一张图片，任务之间让出 50 毫秒；已有结果先返回。复用 Windows 已安装的系统识别器，不下载语言包、不调用翻译或云服务。搜索另准备最长边 2560 的 OCR 副本，遵守识别器 25 MiB／3200 万像素与系统尺寸上限；原件超过此接收上限不再直接排除。缩小或使用无法证明完整文字清晰度的已有 SVG 静态图时记录细节受限。识别文字上限 250,000 字符，超限不静默截断。原生调用最多 30 秒，取消、隐藏、切换查询或关闭空间停止后台任务；队列结束释放 Worker。识别命中保留真实片段；敏感检查原有的不落盘行为不变。

搜索只编码查询文字，再对持久向量分批计算点积并排序；查询向量最多缓存 32 条。当前是精确扫描，没有近似最近邻索引，小样本不能证明十万级图库的延迟。

索引队列完成后释放视觉 Worker；查询 Worker 继续复用文字模型与查询向量。后台编码不会让查询在任务队列中等待，但两个 Worker 的模型内存与原生计算仍需要设备资源。

## 文稿语义搜索试用

文稿复用已保存内容索引的活动来源、当前修订与正文提取预算，覆盖图文／便签、社交稿和视频文档分支。每批最多向 Worker 传 8 篇，每篇正文上限沿用 250,000 字符、当前文字索引正文总预算沿用 8 Mi 字符；超限只编码标题，并保留覆盖不足状态。正文以最多 1,200 个 Unicode 字符、相邻重叠 200 字符的片段编码，每次查询最多推进一段；隐藏、输入法组合、模式或查询变化取消过期请求，只有可见且有效的语义查询才继续补齐。

使用同一模型的纯文字会话，不加载视觉编码器。查询沿用检索前缀，片段使用 `title: {title} | text: {content}`；标题编码最多取 256 个 Unicode 字符，显示仍保留完整标题。向量及片段保存在 `.cache/image-search/content-vectors.sqlite3`，绑定当前修订及模型指纹；重新打开时复用未变化修订，删除、归档或修订变化后不返回旧片段。派生缓存的同步 SQLite 调用限于 Worker，向量每批扫描最多 128 段；没有新增产品数据库迁移。

标题和正文都没有可检索文字、数字或符号的文稿不生成向量；打开既有缓存时仅清理这类空片段，保留有效向量。明确的 ID 查询仍能找到空文稿。

正文索引状态为 `ready` 时，正文确实为空的标题内容按相同分数界线与背景判断分级，不因缺少正文片段强制降为一级。正文索引覆盖不足的语义候选仍标为一级“弱相关”，并保留实际覆盖状态；不能把尚未取得正文当作正文真的为空。明确的关键词／ID 命中仍按实际文字依据展示。

同一文稿只展示一条结果：纯语义选背景校正后排名最高的一段，混合模式存在文字命中时显示对应真实片段。选择后复用现有正文编辑器；语义命中不伪装成原文中存在查询词，也不应用关键词高亮。文字与图片查询各自取消、分页和报告错误。文稿索引的首次完整耗时、完整真实库召回质量与多模型会话的内存尚需专项验证；当前接线和既有回归通过不能证明完整语义质量或性能。

### 文稿背景校正

文稿排序使用 `原始余弦 - 0.75 × 空查询余弦`。空查询保留同一模型的检索任务前缀，只去掉查询正文；每个文稿 Worker 首次有可搜索向量时编码一次并在内存复用，不积累用户查询、不取当前文稿库的平均方向。当前查询不比空查询更接近该片段时，也标为一级“弱相关”。原始分数保留在内部数据中；对外等级按下节规则分类，校正值只负责片段选择和语义排名，不当作概率或新的相似度展示。

纯语义和混合检索的语义通道使用同一校正，在文稿去重与分页前完成；混合检索继续按原有文字依据和 RRF 规则融合。没有针对 `test`、短文本或 emoji 的黑名单，不删除候选，不改变关键词查询、源文稿和已有向量。新增分值只在临时排名表中保存，不增加产品数据库迁移或触发全库重新编码。每批仍读取至多 128 个向量，在同次扫描中计算查询和背景点积，首次背景推理前后检查取消。

权重用于当前 Q8 模型的有限试用：与文稿均值扣减、查询样本均值扣减和完整空查询扣减比较后，选择兼顾误召回与正向找回的部分扣减。它不是已经普遍验证的最优参数；不同模型、长文片段和更多真实任务仍需复核。图片只下调标注界线，本轮不将文稿校正推广到图片或视频。

### 五级相关度

文稿、图片与视频语义结果共用 `SearchRelevance`，显示一根固定宽度的五段横条，填充 1–5 段对应五级；条宽 3rem、高 0.375rem、段间隔 1px。使用现有中性色，填充段深、未填充段浅，不使用字符画、星形、渐变或加载动效。结果行及悬停不显示等级文字或分数；`role="meter"` 的名称与 `aria-valuetext` 通过项目 i18n 提供“相关度”及对应等级，段本身对辅助技术隐藏。强制颜色模式使用系统前景和背景，并保留外轮廓。

无有效分数且没有依据不足标记时不显示相关度条，避免全空条被误读为零相关。ID、标题、文件名、OCR 或视频文字的真实命中仍显示各自依据；附带的已有依据不足标记也用一级短条表示。条是只读指示，不增加焦点停靠或改变整行打开行为。

`src/shared/search-relevance.ts` 集中维护每个通道的四个界线，主进程继续从第一条界线生成弱相关标记；其值与此前一致。直接比较原始分数，不先换算、取整或按查询结果归一化；等于界线时进入较高一级。

| 通道           | 一级：弱相关 | 二级：边缘相关 | 三级：一般相关 | 四级：较高相关 | 五级：高度相关 |
| -------------- | ------------ | -------------- | -------------- | -------------- | -------------- |
| 文稿           | < 0.65       | [0.65, 0.75)   | [0.75, 0.85)   | [0.85, 0.93)   | ≥ 0.93         |
| 图片／视频画面 | < 0.68       | [0.68, 0.77)   | [0.77, 0.86)   | [0.86, 0.94)   | ≥ 0.94         |
| 视频文字       | < 0.70       | [0.70, 0.79)   | [0.79, 0.87)   | [0.87, 0.94)   | ≥ 0.94         |

高等级区间逐步收窄，但这些仍是试用展示界线，尚无等级准确率校准。分级不改变排序、召回或分页；文稿的背景校正与混合融合仍决定具体顺序，等级不代表排序分值，也不据不同通道的相同等级直接比较相关性。

既有 `borderline`（包括空查询背景虚高、正文索引覆盖不足）优先归为一级“弱相关”，即使原始余弦很高或缺失也一样。完整索引的标题内容不因正文为空设置该标记。这里的内部字段是依据不足标记，不对应二级名称“边缘相关”。列表只显示一次等级；视频的全弱相关状态同步使用“弱相关”文案。原始分数和内部标记继续保留在数据契约中，不增加迁移或重新编码。

## 中英文查询前缀

中文、英文和中英混合输入统一采用 `task: search result | query: {原始查询}`。前缀是模型训练约定，不按界面语言翻译，也不先把用户查询翻译成英文。图片直接编码，不附加名称或虚构说明；名称命中由精确匹配另行处理。

[Google 的跨模态检索示例](https://ai.google.dev/gemma/docs/embeddinggemma/fine-tuning-multimodal-embeddinggemma-with-sentence-transformers)使用相同的 `Retrieval-query` / `SearchQuery` 前缀；[任务说明](https://ai.google.dev/gemma/docs/embeddinggemma/inference-embeddinggemma-with-sentence-transformers)区分检索与句子相似度。`task: sentence similarity` 面向另一种任务，不能仅因界面叫“语义搜索”就替换检索前缀。

本轮在固定的 24 张合成图片向量上比较 32 条中英文及混合查询：官方检索前缀、无前缀、句子相似度前缀、自拟 image retrieval 前缀和中文翻译前缀。五种方式的首位命中数相同，不能证明自拟或翻译前缀更好，故保留官方检索前缀。中文否定条件仍失败；这个小样本不代表真实照片、长描述、风格检索或所有否定表达。

### 本次接入范围

- 所有空间的画面与 OCR 准备任务共用一个在途槽，不把原图像素传入 main 或 renderer。准备进程不加载嵌入模型，优先级降低；取消立即终止该进程，单任务最多 45 秒。每 50 毫秒采样进程 RSS，超过 768 MiB 时终止并返回资源待重试；这是采样终止阈值，不是操作系统分配硬配额。渐进／交错解码仍可能瞬间分配较大原生内存。
- 按内容哈希、用途和 `proxy-v1` 复用完整小图。缓存命中校验 PNG 容器及解压数据，不重读原图正文。文件缩放使用当前 Sharp/libvips 的顺序读取及加载阶段缩小能力，最终只输出小图。位图保持原颜色、方向和去透明处理；SVG 固定白底。新能力不改变兼容成功向量的模型指纹。
- SVG 先复用已有且完整校验过的静态 PNG，否则在独立进程中校验 XML 和自包含引用，以 Buffer 交给 librsvg；不传文件基址，不允许脚本、动态标签、外部文件、外部 URL、DTD、处理指令或 CSS 外部依赖。内嵌图片仅允许受限的 PNG/JPEG/WebP data URL。当前 Sharp 0.35.5 源码支持 SVG 加载时缩放，保留原 viewBox 和比例，无需改写源文档，也未放宽通用裁切／导出沙箱。

- 原件独立保留防御限制：位图最多 1 GiB、10 亿像素、最长边 100 万；SVG 文档最多 25 MiB、5 万元素、128 层，内嵌 data URL 累计最多 16 MiB。优先尝试已有派生图后才检查原件限制。这些限制不等同于原来的模型入口门槛。
- 本次没有引入第二套图像依赖，也没有接入任意原图的磁盘像素缓存或系统预览 helper。512 画面降级与受限磁盘回退仍是下面的后续评估项，不能声称已经支持。当前进程资源耗尽保留 `deferred`，不会以普通 `pending` 轮询反复重启，也不会伪装为原件损坏。
- 搜索缓存事务化增加原因、策略和细节字段，每个能力版本只重置旧失败项一次，保留成功向量与 OCR。手动重试只推进可恢复故障；固定格式、尺寸和字节限制等待来源或策略变化。编码／OCR 返回后由主进程再次核对活动身份和内容哈希，再发送窄提交命令；取消、陈旧内容不写失败或结果。
- 画面与文字通道分别返回原因分组、待重试和细节受限数量，受影响图片按身份去重。图片状态不再混入文稿的“无法读取／仅标题”提示。“查看”按需取 30 项并核对当前可见范围及快照，继续复用现有打开原件动作；恢复操作复用搜索刷新。

### 处理入口与职责

在主进程的素材解析与索引调度之间增加一个图片索引输入准备模块，统一核对活动身份、内容哈希、格式、尺寸和取消状态。该模块只协调异步读取、已有沙箱解码器与索引进程；不在 main 或工作区 renderer 解码图片。renderer 仍只提交资产身份和受校验的索引操作，不提交路径或任意解码参数。

准备结果返回原资产身份、原内容哈希、输入策略版本，以及受限派生输入或结构化失败原因。成功提交必须再次核对资产仍活动、内容哈希及任务代际未变化；取消、切换空间或陈旧任务不能覆盖新结果。画面编码和 OCR 分别消费准备结果，复用来源解析和可兼容的派生数据，保持独立输出与失败状态。

### SVG 静态输入

1. 复用 `media/svg-raster-cache.ts` 按原内容哈希查找已有静态 PNG 的方式，使用异步读取和完整校验。只有尺寸、来源和处理策略兼容时才复用；不把列表小缩略图直接当作 OCR 输入。
2. 缓存缺失时，复用 `media/sandboxed-image-decoder.ts` 的窄接口、来源校验、取消、超时和无外部网络的解码环境。画面索引请求最长边 1024 的静态图；OCR 使用独立的较高分辨率配置。搜索派生图使用自己的版本键，不覆盖供导出等流程使用的原尺寸 SVG 静态缓存。
3. 先校验 SVG 文档、引用和依赖。仅接受可自包含渲染的静态内容；不执行脚本或读取外部文件、网络资源。已有可信静态缓存可作为动画的固定代表图；没有固定代表图且不能稳定取得静态画面时返回具体原因。本轮不截取随机动画时刻，也不把 XML 源码或不可见的 `<text>` 直接当作识别文字。
4. 索引仍保存原 SVG 的资产 ID 和内容哈希。新生成的搜索静态图属于可重建缓存，不生成新的素材记录，不触碰原件；派生缓存按内容哈希、处理用途、尺寸与策略版本复用，并沿现有缓存机制限制磁盘占用。

现有沙箱会在解码前检查原始尺寸，通用像素上限为 `4096 × 4096`；请求较小缩略图不会绕过这个检查。SVG 声明画布超限时也先检查可用静态派生图；确需从原 SVG 生成时，为搜索增加明确目标渲染尺寸的窄接口，保留内容复杂度、嵌入资源、执行时间和输出大小校验。不能只改声明宽高而破坏 viewBox、比例或相对单位，也不能放宽所有裁切、导出和水印操作的共享限制；现有接口尚不支持这条大画布路径，实施时须单独验证。

### 大位图与资源预算

画面模型的输入目标继续为最长边 **1024**，按比例保留完整画面，原件保持不变。将当前 **32 MiB／1600 万像素** 的直接编码入口限制保留为受控输入边界；原件超过该边界时交给输入准备模块，不能在素材枚举或缓存同步时先记为 `unavailable`。源文件、缩图任务和模型输入分别校验，缩图器不继承模型的原文件资格限制。

建议按以下顺序选择处理路径；超过普通路径预算表示需要换路径，不是任务已经失败。

| 路径           | 处理与进入条件                                                                                                               | 回退条件                                                                 |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 复用派生图     | 优先读取绑定内容哈希、方向、完整构图与处理版本的已有预览；输出足够清晰即可使用，不需要与原件同尺寸                           | 缓存缺失、过期、裁切或清晰度不满足用途时继续                             |
| 文件直接缩图   | 复用 Sharp/libvips，从文件构造解码与缩放流水线，最后才取得小图像素；JPEG／WebP 使用解码阶段缩小，普通非交错 PNG 使用顺序读取 | 格式需要大块内存、方向变换破坏顺序访问，或普通任务预算不够时进入隔离回退 |
| 受限的隔离回退 | 独立、低优先级、单并发缩图任务；优先评估 libvips 的临时磁盘路径，或能返回真实完整画面的平台预览能力                          | 每种适用策略只尝试一次，按错误类别换路径，不重复触发同一个像素门槛       |
| 较小完整图     | 输出开销或现有预览质量不支持目标尺寸时，可采用最长边 512 等较小完整图，记录尺寸和 `detailLimited`                            | 该降级只解决派生图成本或预览可用性，不解决仍需展开原图的解码内存问题     |
| 最终状态       | 可用输入进入索引；瞬时资源不足标记待重试；损坏、无权访问或所有适用路径均耗尽后才记录最终原因                                 | 保留名称／ID、原件及其他成功通道，不要求用户手动转格式后重新导入         |

现有 `MediaThumbnailCache` 最大尺寸为 512，并包含系统预览回退，但缓存键只有资产 ID 与尺寸，不能不核对内容哈希就作为新索引依据。新增用途应复用其可用能力与调度思路，并补足来源验证；平台返回的图标、裁切图或无明确来源的预览不可采用。系统预览若不能取消或无法约束资源，也不能充当无限等待的兜底。

普通流水线保持现有方向校正、等比缩放、sRGB 和位图透明处理，避免无关改变成功向量。新增 SVG 输入的透明背景采用固定白底并纳入该输入策略版本。画面与 OCR 分别准备输入：画面可用较小完整图，OCR 按系统尺寸及 25 MiB 接收边界另生成较高分辨率的副本；长截图和细字仍需单独验证，不能把 1024 或 512 的画面缩图当作完整文字覆盖。

准备阶段首先读取有界的元信息，检查格式、真实宽高、位深、通道数、交错／渐进标志、方向与帧数，据此选择路径。原文件像素或字节数可以触发调度分流；禁止把 3200 万像素或 32 MiB 继续用作所有原件的统一拒绝条件。异常尺寸和压缩炸弹等完整性检查仍保留，但应与普通路径预算区分，并在失败中标记具体的硬性限制。

新增解码共用一个在途任务槽；任务预算分别覆盖输入读取、解码器内部内存、临时盘、输出、超时和取消。给原生缩图进程设置外部监控与终止边界，不能把 V8 heap 或 `sharp.cache()` 的限制当作全部原生内存限制。临时数据使用空间内受控任务目录，限制磁盘占用、检查剩余空间、原子发布完整派生图，并在完成、取消、失败及下次启动时有界清理。具体配额由代表输入实测后确定，不能假设缩小目标就自动解决源解码成本。

Sharp 的 [输入选项](https://sharp.pixelplumbing.com/api-constructor/)和[缩放选项](https://sharp.pixelplumbing.com/api-resize/)可以支撑普通路径；libvips 的[文件读取策略](https://www.libvips.org/API/8.17/how-it-opens-files.html)说明了 PNG 按行缩小及部分路径的磁盘中间文件机制。应先验证当前绑定能否控制需要的路径与临时目录；若不能，评估随应用分发的窄 libvips helper，不要求用户另装命令行工具。[ImageMagick 像素缓存](https://imagemagick.org/architecture/)作为机制对照，本方案暂不增加第二套通用图像依赖，也不假定磁盘缓存能约束外部解码库的全部内存。

libvips 的[开发检查表](https://www.libvips.org/API/8.17/developer-checklist.html)指出渐进／交错图片可能需要大量内部内存，因此不能把普通 PNG 的结果推广到所有大图。实施时比较普通 PNG、JPEG、交错／渐进格式和长宽比极端的输入，记录峰值 RSS、临时盘、读取量、解码时间与并发查询延迟，再确定普通和隔离路径的预算。

### 失败契约与界面

将编码器的 `vector | null` 和 OCR 的泛化失败逐步改成可区分成功、取消、限制和错误的结果。派生缓存保存稳定原因及结构化参数，例如格式、实际尺寸和限制值；不持久化供界面直出的中英文错误句子。

| 原因                           | 建议代码                                         | 默认重试规则                                           |
| ------------------------------ | ------------------------------------------------ | ------------------------------------------------------ |
| 格式不支持                     | `UNSUPPORTED_FORMAT`                             | 格式或能力策略改变后重检                               |
| SVG 无可用静态输入             | `STATIC_IMAGE_UNAVAILABLE`                       | 来源、静态缓存或能力改变后重检                         |
| 所有适用路径均无法满足硬性限制 | `BYTE_LIMIT` / `PIXEL_LIMIT` / `DIMENSION_LIMIT` | 保存限制所在阶段与已尝试策略，来源或相应限制改变后重检 |
| 当前资源不足                   | `RESOURCE_LIMIT`                                 | 保留待重试状态，资源改变或用户主动重试；不忙循环       |
| 原件不存在或访问失败           | `SOURCE_MISSING` / `SOURCE_UNREADABLE`           | 用户主动刷新重试                                       |
| 解码失败                       | `DECODE_FAILED`                                  | 用户主动重试                                           |
| 执行超时或进程失败             | `INDEX_TIMEOUT` / `INDEX_FAILED`                 | 停止自动重试，保留其他结果                             |
| OCR 平台或识别语言不可用       | `OCR_UNAVAILABLE`                                | 独立能力状态，环境改变后重检                           |

缺少模型、插件关闭或系统 OCR 能力不可用按通道报告，不批量伪装成每个源文件损坏。`CANCELLED` 不写入失败状态；旧缓存缺少原因时先标记原因未知，不从一个空向量猜测具体故障。现有素材解析器会把多种原因压成 `null`，本轮应增加供搜索使用的结构化异步结果，保持其他消费者的原接口兼容。较小完整图成功后仍可提供画面结果，通过独立的 `detailLimited` 标记说明细节受限；资源待重试不混入不可读计数，也不沿普通 pending 轮询持续重新解码。

在搜索契约中为画面和 OCR 分别返回覆盖统计与原因分组；底部按当前模式显示对应通道。总受影响图片数按资产身份去重，两个通道的失败数不能直接相加。原有文稿失败统计保留自己的含义，不能把图片超限计入“文稿仅标题／ID”。混合模式可返回只命中其中一个通道的图片，并同时显示另一通道的缺口。

“查看”复用 shadcn Dialog、ScrollArea 和 Button 展示按需分页的失败项；详情接口只接收当前空间内的类型、模式、原因和游标，并重新校验可见身份。列表展示名称、简短原因和原位置动作，单页最多 30 项；不在初次搜索时发送全部失败项。打开与关闭保留焦点，刷新快照后重新取得稳定列表。文案通过现有英文基准和简体中文语言资源同步维护。

### 旧缓存接续

在可重建的搜索缓存中补充失败原因、输入策略版本和失败时的策略版本，采用幂等、串行的缓存结构升级。通道状态继续独立保存，成功向量与成功 OCR 保留；不修改产品数据库迁移，不在本轮方案阶段递增应用或插件版本。

能力策略版本与模型／向量预处理指纹分开：扩展可接受格式或尺寸只重新检查旧失败项，不令兼容的成功向量失效；真正改变已成功图片的颜色、方向、缩放或模型编码时，必须让受影响向量按新指纹重建，不能用保留缓存掩盖不兼容。

下次可见、允许索引的查询按批重新检查策略过期的失败项；旧缓存原因未知的记录每个新策略版本只重新判定一次。超过旧直接编码门槛的记录先进入派生输入准备流程，只有所有适用路径都不支持或超过硬性预算时才保存最终原因。全局刷新只重试瞬时故障或来源／能力已变化的项目，不把所有 `unavailable` 无条件改成 `pending`。插件停用时不补画面向量，关键词模式仍可使用独立 OCR。派生图增加内容哈希、实际尺寸、用途、清晰度及转换版本；重新查询只复用，不反复读原图。

派生写入核对哈希与策略版本，旧任务不能覆盖新任务；失败详情和统计与结果使用同一快照规则。升级或取消后不存在半写入向量，不要求用户清空整个缓存、重新导入或手动转换原件。

## 视频片段检索第一版

2026-10-09 接入现有搜索工作面的“视频”类型。根据用户后续要求，视频类型直接检索当前空间活动视频的画面与时间文本，不再依赖手动选择来源；查询为空时不启动索引。从关键词模式进入视频类型时使用语义模式，视频内支持语义与混合检索。模型和设备沿用语义搜索配置，读取当前空间视频需允许可选权限 `library.read:active-videos`。

已移除“视频文稿／选择视频”范围行与选择面板，启用和读取授权放在原有搜索设置中；进入视频搜索不隐式授予权限。`library.read:selected-videos` 保留旧显式 ID 接口的有限范围兼容，不授权省略 ID 的全空间查询，也不自动迁移为新权限。旧导航中的 videoIds 不再限制新界面的检索范围。

全部内容中的视频文稿结果仍复用本地化的逐字稿、图文稿和笔记分支名称，普通结果不显示分支与文档的原始 ID；明确按 ID 命中时仍显示身份。逐字稿投影中的毫秒区间转换为播放时间格式，摘要在已有片段内优先取查询词附近的上下文，纯语义模式不因此增加精确文字高亮。只识别逐字稿约定的时间前缀，不猜测普通笔记中的数字含义；不同分支仍分别保留结果和原保存身份。

第一版将字幕按最多 15 秒／1200 字符组合，时间笔记按保存的位置分段，富文本笔记只索引已有时间段标题，不把整篇正文随意绑定到某一时刻；无时间关联的正文继续由原文稿搜索负责。每个来源最多读取 32 个分支、每份修订最多 200 万字符、最多 3000 个文字片段，超出或未覆盖的文字标记覆盖受限。画面和文字调用同一 Q8 模型的单图与文档编码路径，不调用原生多帧输入，也不新增转写任务。

画面基线在每秒内按 250 ms 网格保留真实帧。FFmpeg 保留源 PTS，缓存同时保存 PTS、time base 和容器时间原点，播放器使用归一化后的实际帧时间。解码后等比缩放并补边至 640×640，不裁掉字幕区、不按向量相似度丢帧。这个采样密度不构成短暂事件召回保证，也没有证明运动顺序理解。

解码、文本解析、同步 SQLite 和向量扫描在现有隔离搜索进程的 video 角色中执行。全空间来源按 128 项键集分页枚举，页间让出执行并检查取消；主进程仅集合核对返回页至多 30 个来源或单个预览来源。文件状态检查使用异步 API，并发至多四项；缓存状态集合读取，每次仅解析一份变化文稿的时间文本，其余旧证据立即失效并保持待处理。每次请求推进一个来源的一秒画面或一个文字片段，来源按已处理批次数轮换，文字与画面交替；切换查询、暂停、隐藏页面、停用插件和关闭空间会取消待处理请求。FFmpeg／ffprobe 采用参数数组、禁止网络协议及播放列表解复用，每次解码输出最多四帧（约 4.7 MiB），子进程超时 30 秒，解码线程上限 2。搜索隔离进程的 RSS 监测阈值为 3 GiB；这不是包含 FFmpeg／GPU 的硬内存配额。当前来源身份元数据仍随范围大小增长，不据分页读入宣称总内存恒定。

派生缓存为 `.cache/image-search/video-vectors.sqlite3`，不增加产品数据库迁移。模型与处理策略变化重建缓存；来源哈希或文件大小／修改时间变化清除相应画面，文稿修订变化重建对应文字，已经提交的批次可在暂停或重启后继续。返回结果和打开预览前核对活动文档、来源哈希及修订。结果带视频、证据类型、实际时间和片段文本；选择结果直接设置播放器时间并暂停，画面命中显示毫秒时间码。双击、Enter 或“从此处播放”在 seek 完成后播放，不打开图文编辑器；预览不再提供图文打开按钮。

排名先按同一视频的一秒时间组保留各通道候选，再执行每通道最多 1000 组的候选预算；混合模式用 reciprocal rank fusion 合并，纯语义模式不加词频分。时间组只约束结果展示，缓存仍保留每个采样帧。语义结果只显示上述五级相关度，原始余弦保留在内部数据中，不将等级解释为正确概率，也不据此自动判定目标存在。界面显示已索引帧数、处理时长、暂停／继续及不可用状态，设备设置单独报告视频进程的实际后端和回退状态；不将抽样时长等同于全部画面已理解。

一级“弱相关”目前沿用画面低于 0.68、字幕／笔记低于 0.70 的界线，不删除候选或改变排名。混合检索中的真实词项命中另标文字匹配；整组候选只有弱相关结果时，在列表原有状态区显示简短状态，而不是仅根据当前分页判断。索引待完成、来源不可用或文字覆盖受限时，状态明确限定于已索引范围。第一条界线仅用小型校准样本检查过，后续等级界线仍为试用展示值，尚无留出集质量结论，未标注弱相关不等于确定相关。

同一隔离进程只保留最后一次、至多 1000 项的排名，用于重复查询及分页；每次仍核对活动来源、文件状态、修订和索引进度，快照、查询或模式变化即失效。向量扫描复用对齐的 Float32Array 视图，非对齐数据才复制，不改变点积计算顺序。可选 worker 诊断记录准备／排名耗时、扫描行数和向量字节数，不记录查询或正文。暂停索引会停止推进，但模型资源仍可能驻留；沿用搜索进程空闲五分钟退出规则。

需要可执行的 FFmpeg 和 ffprobe；依次使用配置路径／同目录工具、应用资源目录和 PATH。第一版每秒窗口重新启动解码器；完整短视频观测显示主要成本在逐帧模型推理，仅减少解码进程不能消除这部分成本。未实现连续解码复用、应用启动后的全库后台索引、源哈希跨文档去重、帧图片持久保存或视频转文章接线。搜索缓存中的向量不能直接当作文章配图附件。语义／混合视频检索要求现有模型可用；模型未准备好时，仍可在全部内容中使用文稿关键词搜索。

相关现有测试、类型检查、静态检查与构建通过，用于周边回归。生产隔离 worker 已在既有短视频上完成 Q8／WebGPU 全量采样索引、磁盘缓存重启恢复及查询；同缓存前后比较中，暖态查询和重复查询耗时下降，检查的候选顺序、分数与分页保持一致。另完成同一小样本的 CPU／GPU 成本观测；未完整重跑 CPU 视频索引，亦未证明 GPU 故障时自动回退。详细诊断与运行证据不纳入应用仓。

这些观测绕过应用界面、授权 IPC 和服务外层调度；使用空间外的临时派生缓存，没有修改真实空间的权限和索引。仍未构成取消续跑、来源替换、端到端播放、五分钟自动退出或系统检索质量验收。尚未开展真实应用界面检查、小时级长视频基准或成品包验收；构建成功也不意味着正在运行的应用已加载修改。FFmpeg PTS 命令检查仅核对已有样本的抽帧时间，不替代可变帧率、旋转和非零时间原点素材的验证。

## 视频片段检索接入调研（2026-10-08 的接入前记录）

2026-10-08 核对上游资料、当前源码、已安装的 Transformers.js 4.3.1，以及推荐下载清单对应的处理器配置。以下是产品接入建议；随后进行的独立模型试用不代表应用接线、真实视频效果或成品包验证。需求目标、使用场景和产品取舍维护在共同产品文档的搜索调研主题；本节只维护桌面接点和技术边界。

### 模型与运行时已经具备什么

[Google 文档](https://ai.google.dev/gemma/docs/embeddinggemma)说明 EmbeddingGemma 2 支持视频与其他模态的共享向量表示。[ONNX 模型说明](https://huggingface.co/onnx-community/embeddinggemma-2-ONNX)提供 JavaScript 视频示例。结合当前安装包的源码，可确认以下静态调用链：

```text
由应用解码的有序帧与时间 → RawVideo
→ processor(null, null, null, video)
→ 视频帧经过现有 vision encoder
→ 文本骨干聚合视频 token → sentence_embedding（768 维）
```

`src/main/image-search/model-download.ts` 固定推荐修订为 `daa72c51243991dfcaf9f9137d2c573d8f7790c0`，下载文字骨干和视觉编码器。对应 `processor_config.json` 的 SHA-256 为 `168f6a08522f3ce5dea596d94d003af2fd691742d4f41fe1f9d8cce76bfbf69c`，包含 `video_processor`：每帧预算 140 个 soft token、最多 32 帧、超出后均匀抽样、`add_timestamps: false`。视频画面不需要新增独立视频权重；当前显式关闭的音频编码器不影响纯视觉路径。含声音的检索需要另行准备音频能力，不能据此认定已经覆盖音轨。

安装包 `src/models/embedding_gemma2/` 下的三个实现分别负责输入编排、视频帧预处理和模型运行：

- `processing_embedding_gemma2.js` 的视频是第四个参数。多张图片作为一条图片输入、多个视频作为一个批次，与一个有序视频片段不是同一种输入组织。
- `video_processing_embedding_gemma2.js` 只接收已经解码的帧，并在超出 `max_frames` 时再次抽样；配置中的 `fps` 不会替 Node 端执行解码或保证采样间隔。必须在解码之前限制数量，不能先加载整条长视频再依赖 32 帧上限节省内存。
- 该版本通过 `video.frames.map(frame => frame.image)` 取图像，没有把 `RawVideoFrame.timestamp` 或视频时长加入模型输入。序列顺序保留，但返回向量没有时间定位结果，不能声称模型理解了精确持续时间或自动输出事件边界。
- `modeling_embedding_gemma2.js` 将视频帧送入 `encode_image`，再作为 `video_features` 传给文字骨干。这不同于分别编码图片后计算向量平均值。

`src/utils/video.js` 中的 `load_video()` 依赖浏览器媒体 API，Node 环境明确报错。不能把网页示例中的 `load_video(mp4)` 直接移入现有模型 Worker。应用自行解码后可构建带真实时间的 `RawVideoFrame[]`；跳转所用绝对时间还须独立保存在索引中，不能依赖该处理器保留它。

上述处理器配置已与下载清单哈希核对。独立模型试用复用现有权重；固定 Q8 图在不同输入形状下的兼容性、CPU／WebGPU 故障恢复和真实素材质量仍需分别验证，不能用最新模型页示例或一次前向计算代替本应用验证。

关键画面服务已有同步 `statSync`／`realpathSync` 路径和在宿主中计算帧差的逻辑；扩大到视频库时不能原样搬入主进程批量循环。新路径应将解码、帧处理及模型计算放在受控独立执行进程，使用异步文件访问，不在此调研中顺带修改原服务。

### 解码与分段候选

优先考察现有 FFmpeg 路径：以参数数组启动，限定当前活动来源，解码时按方向、比例和帧数缩小输入，不修改原件。连续片段尽量顺序解码并复用重叠帧，避免每一帧或每一段都重新启动进程、从文件开头读取。长片段任务必须有背压、取消、字节预算和超时；seek 与顺序扫描的取舍取决于实际编码格式和请求范围，需测量后决定。

[FFmpeg 滤镜文档](https://ffmpeg.org/ffmpeg-filters.html)可参考 `fps`、`select`、`showinfo`。采样计划、实际帧 PTS 和播放器时间的映射应明确，处理可变帧率、非零起始时间和尾帧；不能用帧序号除以声明帧率冒充准确定位。固定频率滤镜可能复制或丢弃帧，片段边界与实际采样证据分别保存。

已有 FFmpeg 解析顺序是显式环境路径、应用资源路径、系统 PATH，源码还保留待选择可分发 sidecar 的说明，不能宣称所有成品安装均有可用解码器。能力不可用时保留已有文字结果并报告视频处理状态；本次不安装或打包新的解码器。

项目已安装 Mediabunny 1.53.0，目前在该链路使用它探测音轨。[官方说明](https://mediabunny.dev/guide/introduction)及 [server 扩展](https://mediabunny.dev/guide/extensions/server)提供另一条路线：浏览器编解码与 Node 端原生能力分别部署。当前未安装 `@mediabunny/server`，能读容器信息不等于 Node 中已有视频解码器。可以作为后续替代方案比较，但没有依据因已安装核心包就绕到 renderer 做后台全库抽帧。

建议以固定短窗口建立基线，再比较利用镜头边界的方案。镜头切换可减少无关画面混入；静态讲解可能很久不切镜，快速剪辑则可能过碎，因此仍需片段时长上下界。现有关键画面候选可作预览或采样补充，不代替全时段覆盖。

作为待验证起点，可比较 **12 秒窗口、10 秒步长、约每秒一帧**，每次仅编码一个片段；尾段使用实际长度。不是产品默认值或最优参数，短暂动作可能仍被漏采样。保留单帧检索基线，比较后再确定固定窗口、重叠量、镜头辅助和抽帧密度。

### 自适应步长、连续去重与回补（算法候选，未接入产品）

本节将“检查变化的时间间隔”“送入模型的帧间隔”和“长期保存的代表帧”分别控制。以下是结合当前接点提出的工程方案，不是某篇论文已经验证过的完整算法。独立原型的离线候选检查与产品接入分别判断，尚未完成本应用的效果或性能验收。

| 算法／实现                                                                                                                                         | 实际做什么                                                                             | 可借鉴部分与边界                                                                                                                                                                          |
| -------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [FFmpeg `mpdecimate`](https://ffmpeg.org/ffmpeg-filters.html#mpdecimate)，[7.1 源码](https://ffmpeg.org/doxygen/7.1/vf__mpdecimate_8c_source.html) | 用像素块差异过滤近似重复帧；`hi`、`lo`、`frac` 控制变化判定，`max` 限制连续丢弃数量    | 最接近连续重复只保留代表帧；处理已解码帧，不负责语义、动态 seek 或区间回补。`max` 按输入帧数计，时间上限应另按 PTS 控制。部署前核对实际解码器的选项，不能假定最新在线文档的全部功能均可用 |
| [MGSampler，ICCV 2021](https://arxiv.org/abs/2104.09952)，[作者实现](https://github.com/MCG-NJU/MGSampler)                                         | 从相邻图像或浅层特征差异获得运动分布，在累计分布上分层采样；固定帧数更多分配给运动片段 | 适合离线窗口内分配有限帧预算。原研究面向裁剪后的动作视频，不是直接实现在线步长翻倍，也不能把静态片段视为没有检索价值                                                                      |
| [Reducto，SIGCOMM 2020](https://github.com/reducto-sigcomm-2020/reducto)                                                                           | 以低成本特征差异先过滤，再根据内容与查询效果适配过滤策略                               | 借鉴在昂贵推理之前筛选。原系统依赖特定查询的准确性反馈；没有这些反馈时，不能声称任意文字搜索都保持同样召回                                                                                |
| [PySceneDetect `AdaptiveDetector`](https://www.scenedetect.com/docs/latest/api/detectors.html#adaptivedetector)                                    | 以相邻画面变化相对滚动均值的偏离检测切镜                                               | 可辅助识别切换和降低持续相机运动引起的误报；这里“自适应”的是变化判定，不是采样时间步长，也不覆盖镜头内部所有事件                                                                          |
| [AKS，CVPR 2025](https://arxiv.org/abs/2502.21271)，[作者实现](https://github.com/ncTimTang/AKS)                                                   | 综合候选帧与问题的相关性、时间覆盖，通过递归划分选择有限关键帧                         | 更适合搜索命中后、已有查询的局部选帧；预建通用索引时尚无查询，不能照搬为唯一的初始过滤器。递归选择已有候选也不等于重新解码漏掉的帧                                                        |

建议先比较“顺序低成本扫描 → 选择代表帧 → 按需编码”的两层处理。低分辨率检查可以更密，所选画面再以模型需要的分辨率提取；不先对全部检查帧做 Embedding 后才判断是否重复，否则只能减少存储，已经支付的编码成本无法收回。全画面差异宜结合局部块变化，避免小物体或文字变化被平均值淹没；感知哈希、结构相似度和语义余弦都只能作为候选信号，阈值需要用目标素材校准。

一个待验证的控制方式如下，其中 `h` 是变化检查的最大间隔，`delta` 是普通编码候选的间隔，两者不是同一变量：

```text
持续按不大于 h 的间隔检查低分辨率画面，记录真实 PTS 与变化分数
同时比较“上一检查帧”和“当前连续段的代表帧”，观察累计变化
连续 k 次均低于低阈值：delta = min(2 * delta, deltaMax)
变化超过高阈值、累计变化超限或出现切镜：
    delta = max(delta / 2, deltaMin)，立即保留变化候选
    回看最近尚未确定的区间，优先补变化峰及其前后画面
    如需细化边界，再从原件提取中点并检查子区间
中间状态保持当前步长；变化候选优先于下一次普通候选的计划时刻
连续冗余只延长该出现记录的观察范围，不重复编码相同内容
```

低阈值小于高阈值，以迟滞减少来回切换；放大步长需要连续稳定，缩小可以立即触发。翻倍、减半和连续次数只是控制器候选，不是上述论文的统一规则或产品默认值。变化检查的最大间隔不能随 `delta` 无限增大：稀疏端点甚至再加一个中点，也无法排除间隙中短暂出现又消失的内容。更密检查仍受目标大小、画面分辨率和判定阈值限制，不能承诺不漏事件。

离线索引可采用更直接的窗口方案：先取得窗口内低成本变化序列，再借鉴 MGSampler，按累计变化量分配剩余帧预算。建议另外保留时间覆盖、切换前后和已发现事件，静态窗口回退为少量代表帧；将时间覆盖与运动权重混合属于本项目的候选改造，并非论文原算法。必要帧超过预算时拆分窗口或明确降级，不让处理器在末端均匀抽样时悄悄丢掉它们。

回补优先利用有字节上限的短时缓冲或已有变化记录，在有限区间顺序提取；递归深度、最小间隔、总补帧数、源读取量与时间均需有预算。不以一串独立 FFmpeg 进程逐点 seek。[FFmpeg 文档](https://ffmpeg.org/ffmpeg.html)说明滤镜处理的是解码后的帧，精确 seek 还可能从更早的可寻址位置解码并丢弃中间部分。因此缩图、`fps` 或重复帧过滤不等于同等减少解码量；两遍扫描与短缓冲单遍处理应使用相同数据测量后取舍。

复用当前实现时需要注意：`key-change-service.ts` 使用 160×90 灰度检查，整段最多扫描 1,800 帧并选择最多 24 张候选；步长由视频总长决定。帧差计算跳过底部约 22% 及边缘，这可能漏掉字幕和底部控件的变化。这些是现有关键画面用途的取舍，不能成为通用视频检索默认值；新采样器应保持有界处理，但按窗口与目标时间精度控制覆盖。

连续段保存代表帧的实际 PTS、连续段身份、已观察时间范围及检查策略；未细化的切换只能保存边界所在区间，不把相邻样本时间当作精确事件起止。需要边界预览时保留首尾画面，近似重复不等于像素完全一致；同画面在别处重现可复用计算，出现记录必须分开。原件不变，未选中的派生帧在退出有限缓冲后释放，不作为正式素材入库。

若后续将不等间距帧送入原生视频编码，还须单独验证：当前处理器没有把帧时间或持续时间送入模型，保留顺序不代表保留速度和持续时长。跳转时间由外部索引保存，采样调整也不能解决模型本身的时序识别不足。

候选评估应比较固定间隔、连续去重加时间覆盖、两层自适应三条路线，并为短暂 A→B→A、渐变、镜头抖动、闪光、小物体、字幕变化和重复动作分别记录漏检。用独立的更密参考检查与人工确认目标，衡量片段 Recall@K、定位误差、实际编码次数／帧 token 数、解码帧数、读取字节、seek 次数、总耗时、峰值内存和派生存储。同一批近乎静态或精确重复的合成素材不能证明真实视频收益；扫描或回补触及预算的区间也不能记成完整覆盖。

### 输入预算和索引成本

[Google 模型卡](https://huggingface.co/google/embeddinggemma-2)给出的共享上下文为 8192 token，默认视频帧预算为 140 token。[ONNX 导出说明](https://huggingface.co/onnx-community/embeddinggemma-2-ONNX)另提示 WebGPU 某些内核存在约 2700 token／批次的调度边界。这是上游运行注意事项，不能当作本机 Q8 的已验证硬限制或安全保证。

按上述候选，12 帧视觉 token 约为 1680，实际还包含边界 token；应检查处理器实际产物，并留预算余量，不直接使用默认的 32 帧。帧数、soft token 数、解码后像素字节和推理内存分别限制。模型权重文件大小不是峰值运行内存，多个隔离会话也不会自动共享全部权重。

按每 10 秒产生一个片段粗算，100 小时约 36,000 条向量，768 维 Float32 的纯向量约为 **105.5 MiB**；每秒保留一条单帧向量则约为 **1.03 GiB**。两者均不包含 SQLite、元数据、预览、模型或临时帧。这仅是容量算术，不是磁盘实测，也不证明多帧推理更快。重叠窗口会增加模型处理的帧 token，只有解码和中间帧可能复用。

缓存以来源内容哈希、模型／量化指纹、采样和预处理版本、片段起止时间形成身份；另存实际采样时刻、原件身份、可见关系和通道状态。建议独立的可重建片段表／缓存，不将派生帧作为正式图片资产写入图库，不为了复用现有图片结果而丢失视频来源。删除、替换或撤销活动关系后，迟到任务不得提交，原有结果也不能继续打开失效来源。

首轮可复用 SQLite 精确向量扫描，先测真实数量下的查询延迟、读取量和内存，再判断是否需要近似索引。现有每批 128 条只约束单批工作，不能据此推定总查询足够快。缓存帧应有总磁盘预算和清理策略，通常只保留必要预览及重建依据，不默认长期保存所有解码帧。

### 抽帧缓存、笔记采用与 WebP（接入建议，未实施）

缓存选中的代表帧可同时服务搜索预览、关键画面和笔记选帧；只用于低成本变化检查的帧保留在有限缓冲，不全部落盘。向量缓存与画面缓存分别管理：清理预览不应要求重算向量，已有模型输入也不必先有损压缩、再解码来完成当前次编码。磁盘压缩不能减少相同尺寸图片解码后的像素内存。

现有代码已经有“候选文件 → 持久图片资产 → 正文媒体绑定”的部分接点，但格式与缓存入口尚未统一：

- `video-documents/key-change-service.ts` 的关键画面是 JPEG；`captureFrame()` 每次按请求时间调用 FFmpeg，缩放至 960×960 范围，暂存后调用 `ensurePrivateVideoDocumentEvidenceImage()`，返回带资产 ID、时间和 MIME 的媒体绑定。当前手动路径没有先查询可复用的选帧缓存。
- `database/video-documents/video-document-repository.ts` 的 `ensurePrivateEvidenceImage()` 仅接受 `.jpg`，写入对象存储并按文件内容哈希复用 JPEG 资产。资产来源为 `VIDEO_DOCUMENT_DERIVED`，不会仅凭来源类型就向其他功能公开；改成 WebP 需要同步格式验证、MIME、文件扩展名、返回数据与消费者，不能只改编码器。
- `video-documents/generation-service.ts` 已将生成过程选中的关键画面入库；renderer 的视频笔记保存 `mediaBindings`，图片编辑入口接受 WebP。`video-documents/export-service.ts` 的 DOCX 导出已有 WebP 转 PNG 的分支；这些静态接点不代表新增抽帧 WebP 路径已验收。

建议按来源内容哈希、视频流、实际帧 PTS／时间基准、方向与颜色处理、目标尺寸、编码参数和处理版本识别派生画面；请求时间与实际取得时间分开保存。缓存查找可复用足够清晰的同帧变体，低清预览不能冒充高清采用图。与模型无关的帧缓存不绑定模型版本，向量缓存仍包含模型及输入预处理指纹。压缩参数变化时，旧采用图保持不变。

临时缓存按总字节预算清理；正在预览、编码或准备写入的文件使用短期保留，避免读取或采用过程中被清走。插入草稿后沿用编辑器的草稿媒体保留，保存成功前完成持久文件及媒体关系写入；失败不得留下已保存正文指向临时路径。采用图按当前正文、其他使用位置和仍保留修订的引用生命周期管理。内容哈希用于精确复用，相似度仅用于候选去重，不能用近似图片替换作者指定的帧。

[WebP 官方资料](https://developers.google.com/speed/webp/docs/compression)说明它支持有损与无损压缩；项目依赖 Sharp 0.35.5，[其输出 API](https://sharp.pixelplumbing.com/api-output/#webp)已提供 `quality`、`lossless`、`nearLossless` 和 `effort`。可从以下配置开始比较，尚不作为产品默认值：

| 用途                   | 格式与质量候选                                                                   | 保留方式                                   |
| ---------------------- | -------------------------------------------------------------------------------- | ------------------------------------------ |
| 搜索／选帧缩略预览     | 长边 640–960，保持比例且不放大；有损 WebP，`quality: 80`、`effort: 3` 起步       | 只缓存选中画面，允许清理及重建             |
| 普通摄影画面的笔记插图 | 缓存清晰度满足用途时复用；不足时从原视频提取更大尺寸，比较有损 WebP 的质量与体积 | 采用后按持久附件保存                       |
| 小字、代码、表格与图表 | 优先比较无损 WebP 与 PNG，并保留足以阅读的尺寸                                   | 不以缩小文字或近无损模式代替确切的无损要求 |

新画面优先从视频解码像素直接生成目标格式，避免“先有损 JPEG，再有损 WebP”的二次损失。现存已采用 JPEG 不做批量转码；有损 WebP 的 `quality: 100` 也不等于 `lossless: true`。无损是相对于编码前的像素，不能恢复视频原有压缩、缩图或颜色转换已经丢失的信息。编码在受控执行进程中有界进行，不让每个消费者分别生成一份相同文件。

实际收益需用同一批真实画面比较 JPEG、WebP 有损和 WebP 无损／PNG，分别记录编码与解码耗时、字节数、复用命中、峰值内存、小字可读性及检索效果；不将上游压缩比例套成本项目结果。后续实现还需验证缓存淘汰、草稿放弃、保存失败、多处引用、历史修订、来源缺失和导出。当前仅完成资料及源码核对，未切换编码格式、写入新缓存或执行压缩评测。

### 检索、时间定位与验证顺序

文字查询继续采用既有任务前缀；每个片段得到独立向量。字幕、笔记和画面分别检索并保存命中类型；混合模式可复用排名融合思路，不直接相加或平均跨通道原始分数。视频需独立校准相关性，不能沿用图片 `0.705` 的试用标线。单帧基线若按最大分数聚合，也须检查长视频因候选更多而更容易产生高分误报的偏差。

先取相关片段，再按来源聚合展示，保留少量有依据的时间范围；重叠片段去重不能抹掉互不相邻的不同命中。覆盖同时表达已处理时间区间和采样密度，“全时长均已抽样”不等于所有帧或全部动作已被理解。未处理、细节受限、来源不可用和确实无命中分别表达。
